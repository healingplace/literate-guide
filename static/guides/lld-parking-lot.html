LLD Study Guide — Parking Lot System

Low level design walkthrough in C# / .NET — entities, interfaces, patterns, concurrency, extensions

Clarifying Questions to Ask First

In an interview, spend 2 to 3 minutes here out loud. It signals you don't jump straight to code, and it narrows the scope so you don't over-engineer.
  • How many vehicle types? (motorcycle, car, bus/truck are the standard three)
  • Multiple spot sizes, and can a larger vehicle use a smaller spot's tier? (usually no, but a bus might need multiple contiguous large spots)
  • Single level or multiple floors?
  • Pricing model: flat rate, per-hour, or tiered by duration?
  • Payment at entry or at exit?
  • Do we need to support reservations, or just walk-in allocation?
  • Concurrent entry at multiple gates: does allocation need to be thread-safe?

Functional Requirements (assumed for this walkthrough)

  • Support 3 vehicle types: Motorcycle, Car, Bus
  • Support 3 spot sizes: Small, Medium, Large
  • Multiple floors, each with a fixed count of spots per size
  • Vehicle enters, gets assigned nearest available valid spot, receives a ticket
  • Vehicle exits, pays based on duration, spot is freed
  • Display available spot count per floor per size

Non-Functional Requirements

  • Thread safety for concurrent entry/exit across multiple gates
  • Extensible pricing (flat vs. hourly vs. tiered) without modifying core allocation logic
  • Extensible allocation strategy (nearest-first vs. fill-lowest-floor-first)

Key Design Decisions

Composition over inheritance for ParkingLot → Floors → Spots. A ParkingLot "has" floors, a floor "has" spots. This isn't an inheritance chain.
Inheritance for Vehicle types. Motorcycle, Car, Bus all share the contract "what size spot do I need", which varies by type, this is a legitimate polymorphism case.
Strategy pattern for both pricing and allocation. These are the two axes interviewers usually push on ("what if pricing changes to per-minute after the first hour?"). Isolating them behind interfaces means ParkingLot never changes.

Vehicle Hierarchy

public abstract class Vehicle
{
    public string LicensePlate { get; }
    public abstract VehicleType Type { get; }
    public abstract SpotSize RequiredSpotSize { get; }

    protected Vehicle(string licensePlate)
    {
        LicensePlate = licensePlate;
    }
}

public class Motorcycle : Vehicle
{
    public Motorcycle(string plate) : base(plate) { }
    public override VehicleType Type => VehicleType.Motorcycle;
    public override SpotSize RequiredSpotSize => SpotSize.Small;
}

public class Car : Vehicle
{
    public Car(string plate) : base(plate) { }
    public override VehicleType Type => VehicleType.Car;
    public override SpotSize RequiredSpotSize => SpotSize.Medium;
}

public class Bus : Vehicle
{
    public Bus(string plate) : base(plate) { }
    public override VehicleType Type => VehicleType.Bus;
    public override SpotSize RequiredSpotSize => SpotSize.Large;
}

ParkingSpot

public class ParkingSpot
{
    public string Id { get; }
    public SpotSize Size { get; }
    public bool IsOccupied { get; private set; }
    public Vehicle? ParkedVehicle { get; private set; }

    private readonly object _lock = new();

    public ParkingSpot(string id, SpotSize size)
    {
        Id = id;
        Size = size;
    }

    public bool TryAssign(Vehicle vehicle)
    {
        lock (_lock)
        {
            if (IsOccupied) return false;
            ParkedVehicle = vehicle;
            IsOccupied = true;
            return true;
        }
    }

    public void Release()
    {
        lock (_lock)
        {
            ParkedVehicle = null;
            IsOccupied = false;
        }
    }
}

Ticket

public class Ticket
{
    public string Id { get; } = Guid.NewGuid().ToString();
    public Vehicle Vehicle { get; }
    public ParkingSpot Spot { get; }
    public DateTime EntryTime { get; }
    public DateTime? ExitTime { get; set; }

    public Ticket(Vehicle vehicle, ParkingSpot spot)
    {
        Vehicle = vehicle;
        Spot = spot;
        EntryTime = DateTime.UtcNow;
    }
}

Allocation Strategy (Strategy Pattern)

public interface ISpotAllocationStrategy
{
    ParkingSpot? FindSpot(IEnumerable<ParkingFloor> floors, Vehicle vehicle);
}

public class NearestFirstAllocation : ISpotAllocationStrategy
{
    public ParkingSpot? FindSpot(IEnumerable<ParkingFloor> floors, Vehicle vehicle)
    {
        foreach (var floor in floors.OrderBy(f => f.Level))
        {
            var spot = floor.FindAvailableSpot(vehicle.RequiredSpotSize);
            if (spot != null) return spot;
        }
        return null;
    }
}

Pricing Strategy (Strategy Pattern)

public interface IPricingStrategy
{
    decimal CalculateFee(Ticket ticket, DateTime exitTime);
}

public class HourlyTieredPricing : IPricingStrategy
{
    private static readonly Dictionary<VehicleType, decimal> HourlyRate = new()
    {
        { VehicleType.Motorcycle, 2.00m },
        { VehicleType.Car, 4.00m },
        { VehicleType.Bus, 8.00m }
    };

    public decimal CalculateFee(Ticket ticket, DateTime exitTime)
    {
        var duration = exitTime - ticket.EntryTime;
        var billableHours = (int)Math.Ceiling(duration.TotalHours);
        billableHours = Math.Max(billableHours, 1);
        return billableHours * HourlyRate[ticket.Vehicle.Type];
    }
}

ParkingFloor

public class ParkingFloor
{
    public int Level { get; }
    private readonly List<ParkingSpot> _spots;

    public ParkingFloor(int level, List<ParkingSpot> spots)
    {
        Level = level;
        _spots = spots;
    }

    public ParkingSpot? FindAvailableSpot(SpotSize size) =>
        _spots.FirstOrDefault(s => s.Size == size && !s.IsOccupied);

    public int AvailableCount(SpotSize size) =>
        _spots.Count(s => s.Size == size && !s.IsOccupied);
}

ParkingLot (Coordinator)

public class ParkingLot
{
    private readonly List<ParkingFloor> _floors;
    private readonly ISpotAllocationStrategy _allocationStrategy;
    private readonly IPricingStrategy _pricingStrategy;
    private readonly ConcurrentDictionary<string, Ticket> _activeTickets = new();

    public ParkingLot(
        List<ParkingFloor> floors,
        ISpotAllocationStrategy allocationStrategy,
        IPricingStrategy pricingStrategy)
    {
        _floors = floors;
        _allocationStrategy = allocationStrategy;
        _pricingStrategy = pricingStrategy;
    }

    public Ticket? Enter(Vehicle vehicle)
    {
        var spot = _allocationStrategy.FindSpot(_floors, vehicle);
        if (spot == null || !spot.TryAssign(vehicle))
            return null; // lot full, or lost a race to another gate

        var ticket = new Ticket(vehicle, spot);
        _activeTickets[ticket.Id] = ticket;
        return ticket;
    }

    public decimal Exit(string ticketId)
    {
        if (!_activeTickets.TryRemove(ticketId, out var ticket))
            throw new InvalidOperationException("Unknown ticket");

        ticket.ExitTime = DateTime.UtcNow;
        var fee = _pricingStrategy.CalculateFee(ticket, ticket.ExitTime.Value);
        ticket.Spot.Release();
        return fee;
    }
}
Note the retry gap: TryAssign can fail if two gates raced for the same spot found via FindAvailableSpot. A production version would loop or re-query on failure. Mentioning this out loud in an interview is a strong signal.

Patterns Used and Why

Strategy allocation + pricing

Both "how do we pick a spot" and "how do we compute a fee" are things that change independently of the rest of the system. Wrapping each behind an interface means ParkingLot never needs modification when the business changes a pricing tier or wants a different allocation heuristic. This is the single most commonly probed pattern in this problem.

Factory (optional) vehicle creation

If entry gates need to construct a Vehicle from a scanned plate and detected type, a small VehicleFactory centralizes the switch on vehicle type so callers don't do it inline. Not strictly required if vehicles are passed in already constructed, worth mentioning as an option.

Singleton (careful framing) ParkingLot instance

A physical parking lot naturally has one instance. If asked to make it a Singleton, prefer constructor-based dependency injection registered as a singleton service in .NET's DI container over a static Instance property. Classic Singleton is harder to test and creates hidden global state, worth flagging as a tradeoff if the interviewer pushes.

Observer (extension point)

If asked "how would you notify a display board when a floor fills up", this is where Observer fits: ParkingFloor raises an event, a DisplayBoard subscriber updates without the floor knowing anything about displays.

Interviewers often ask "which pattern did you use and why" as a direct follow-up. Have the one-sentence justification ready for Strategy specifically, since it is the load-bearing pattern here.

Where Concurrency Actually Matters

  • Spot assignment race: two gates find the same "available" spot at once. Handled with a per-spot lock inside TryAssign, the check-and-set has to be atomic, not just the read.
  • Active ticket tracking: use ConcurrentDictionary rather than Dictionary for _activeTickets, since entry and exit happen from different gate threads concurrently.
  • Floor-level counts: if you expose a live "spots available" counter for a display board, prefer computing it on demand (as shown) over maintaining a separate mutable counter that can drift out of sync with actual spot state.

What to Say if Pushed Further

If the interviewer asks "what if this needs to scale across multiple parking lot locations with a shared backend", that's the signal to pivot from LLD to HLD: talk about a database-backed spot reservation with optimistic concurrency (a version column) instead of in-memory locks, and mention this is exactly the kind of optimistic vs. pessimistic concurrency distinction from your SQL Server prep.

Common Mistake to Avoid

Don't lock the entire ParkingLot or ParkingFloor on every entry. That serializes all gates behind one lock and kills throughput. Lock at the spot level, the smallest unit of contention.

Gap to Acknowledge if Asked

This design doesn't handle payment processing itself, only fee calculation. If asked to extend it, introduce an IPaymentProcessor interface and treat it the same way as pricing: injected, swappable, and outside the core allocation logic.

30-Second Verbal Summary (for opening the answer)

"I'd model ParkingLot as owning Floors, Floors owning Spots. Vehicle types drive required spot size through polymorphism. I'd isolate the two things that change most, spot allocation and pricing, behind Strategy interfaces so the core coordinator never needs to change. For concurrency, I'd lock at the individual spot level rather than the whole lot, and use a ConcurrentDictionary for active tickets since gates operate independently."
