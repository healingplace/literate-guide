LLD Study Guide — Elevator System

Low level design walkthrough in C# / .NET — scheduling, state machine, patterns, concurrency, extensions

Clarifying Questions to Ask First

This problem is a state machine and a scheduling algorithm wearing a building's clothes. Nail down scope before writing a single class.
  • How many elevators, how many floors?
  • Are there separate up/down buttons per floor (external requests), plus a panel inside each car (internal requests)?
  • Single scheduling strategy, or should it be pluggable (nearest car, least busy, zone-based)?
  • Does the elevator need to support express/service floors, or weight limits?
  • Is this a single building, or do we need to model a bank of elevators sharing one dispatcher?
  • Do we need to simulate movement over time, or just track state transitions?

Functional Requirements (assumed for this walkthrough)

  • N elevators serving M floors
  • External request: a floor button press with a desired direction (Up/Down)
  • Internal request: a passenger inside the car presses a destination floor
  • A central dispatcher assigns each external request to the best available elevator
  • Each elevator moves one floor at a time, stopping to pick up/drop off along its path
  • Doors open at every stop that matches a pending request

Non-Functional Requirements

  • Thread safety: multiple floor buttons can be pressed concurrently across the building
  • Extensible dispatch strategy (nearest-car-first today, could change to zone-based tomorrow)
  • Elevator state transitions must be well-defined and never contradictory (can't be Moving and DoorOpen at once)

Key Design Decisions

Elevator owns its own request queue and state transitions. The controller doesn't micromanage movement, it only decides which elevator gets a new external request. This separation is what keeps the design testable.
State as an explicit enum, not booleans. Resist the urge to model this with isMoving / isDoorOpen flags. A single ElevatorState enum makes invalid combinations (moving with doors open) structurally impossible.
Dispatch strategy isolated behind an interface. "Nearest idle car" is the default, but this is the second most commonly probed extension point after the parking lot's pricing strategy, so it should never be hardcoded into the controller.

Elevator

public class Elevator
{
    public int Id { get; }
    public int CurrentFloor { get; private set; }
    public Direction CurrentDirection { get; private set; } = Direction.None;
    public ElevatorState State { get; private set; } = ElevatorState.Idle;

    private readonly SortedSet<int> _upStops = new();
    private readonly SortedSet<int> _downStops = new(Comparer<int>.Create((a, b) => b.CompareTo(a)));
    private readonly object _lock = new();

    public Elevator(int id, int startFloor = 0)
    {
        Id = id;
        CurrentFloor = startFloor;
    }

    public void AddStop(int floor)
    {
        lock (_lock)
        {
            if (floor > CurrentFloor) _upStops.Add(floor);
            else if (floor < CurrentFloor) _downStops.Add(floor);
            if (State == ElevatorState.Idle) CurrentDirection = floor > CurrentFloor ? Direction.Up : Direction.Down;
        }
    }

    // Called on each simulation "tick"; moves one floor toward the next stop
    public void Step()
    {
        lock (_lock)
        {
            var stops = CurrentDirection == Direction.Up ? _upStops : _downStops;

            if (stops.Count == 0)
            {
                State = ElevatorState.Idle;
                CurrentDirection = Direction.None;
                return;
            }

            State = ElevatorState.Moving;
            var nextStop = stops.Min == default ? stops.First() : stops.First();

            CurrentFloor += CurrentDirection == Direction.Up ? 1 : -1;

            if (CurrentFloor == nextStop)
            {
                stops.Remove(nextStop);
                State = ElevatorState.DoorOpen; // caller flips back to Moving/Idle next tick
            }
        }
    }
}
This is a simplified SCAN-style sweep: keep moving in the current direction, servicing stops in order, and only reverse once the queue in that direction empties. It intentionally skips picking up opposite-direction requests mid-sweep, that nuance belongs in the follow-up tab.

Dispatch Strategy (Strategy Pattern)

public interface IDispatchStrategy
{
    Elevator? SelectElevator(IEnumerable<Elevator> elevators, ExternalRequest request);
}

public class NearestCarStrategy : IDispatchStrategy
{
    public Elevator? SelectElevator(IEnumerable<Elevator> elevators, ExternalRequest request)
    {
        return elevators
            .Where(e => e.State == ElevatorState.Idle || IsMovingTowards(e, request))
            .OrderBy(e => Math.Abs(e.CurrentFloor - request.Floor))
            .FirstOrDefault();
    }

    private static bool IsMovingTowards(Elevator e, ExternalRequest request)
    {
        if (e.CurrentDirection == Direction.Up && request.DesiredDirection == Direction.Up)
            return e.CurrentFloor <= request.Floor;
        if (e.CurrentDirection == Direction.Down && request.DesiredDirection == Direction.Down)
            return e.CurrentFloor >= request.Floor;
        return false;
    }
}

ElevatorController

public class ElevatorController
{
    private readonly List<Elevator> _elevators;
    private readonly IDispatchStrategy _dispatchStrategy;

    public ElevatorController(List<Elevator> elevators, IDispatchStrategy dispatchStrategy)
    {
        _elevators = elevators;
        _dispatchStrategy = dispatchStrategy;
    }

    public bool RequestElevator(ExternalRequest request)
    {
        var chosen = _dispatchStrategy.SelectElevator(_elevators, request);
        if (chosen == null) return false;

        chosen.AddStop(request.Floor);
        return true;
    }

    public void SelectFloor(int elevatorId, InternalRequest request)
    {
        var elevator = _elevators.First(e => e.Id == elevatorId);
        elevator.AddStop(request.DestinationFloor);
    }

    public void Tick()
    {
        foreach (var elevator in _elevators)
            elevator.Step();
    }
}

Patterns Used and Why

Strategy dispatch algorithm

Nearest-car is the default, but real systems switch to zone-based or load-balanced dispatch depending on building traffic patterns. Isolating it behind IDispatchStrategy means ElevatorController never changes when the business swaps the algorithm.

State Pattern (conceptual) Elevator lifecycle

Even implemented here as a simple enum with guarded transitions, this is fundamentally the State pattern: behavior (what Step() does) depends on current state, and transitions are constrained (can't go DoorOpen → DoorOpen). If pushed for a "purer" OOP version, mention that each state could become its own class implementing a shared IElevatorState interface with a Handle() method, trading a bit of simplicity for stronger enforcement of valid transitions.

Observer (extension point)

A natural fit if asked "how would floor displays show which direction each car is going": each Elevator raises a state-changed event, and a FloorDisplay subscriber updates without the elevator knowing displays exist.

Singleton (careful framing) ElevatorController

Same caution as the parking lot: if asked to make the controller a Singleton, prefer DI-registered singleton lifetime over a static Instance, for testability.

The dispatch strategy is the load-bearing pattern here, same role Strategy played for pricing in the parking lot. Expect at least one "what if the algorithm changes" follow-up.

Where Concurrency Actually Matters

  • Concurrent button presses: multiple floor buttons across the building can fire at the same instant. AddStop locks per-elevator so its stop queues stay consistent under concurrent dispatch calls.
  • Dispatch vs. movement race: a request could be routed to an elevator the instant before it starts moving away. Locking the elevator's internal state during both AddStop and Step prevents the queues from being read mid-mutation.
  • Multiple controllers is unnecessary: unlike the parking lot's multi-gate scenario, there's naturally one controller per bank of elevators, so the bigger concurrency surface here is inside each Elevator, not across elevators.

State Transition Rules Worth Stating Out Loud

Idle → Moving (new request arrives) → DoorOpen (reaches a stop) → Moving (more stops in same direction) or Idle (queue empty). Saying this sequence explicitly during the interview demonstrates you've actually thought through the state machine rather than hand-waving state as "just a status field".

Common Mistake to Avoid

Don't let the controller directly set an elevator's floor or state. If ElevatorController reaches into Elevator internals to force a floor change, you've broken encapsulation and made the state machine impossible to reason about independently. All mutation should go through AddStop and Step.

Likely Follow-Up Questions

QuestionHow to Answer
Pick up passengers going the same direction mid-sweepExtend Step to check for matching-direction requests at the current floor before continuing past it, this is the real SCAN/LOOK algorithm refinement
Add weight limitsAdd a Capacity and CurrentLoad to Elevator; AddStop or a boarding call rejects if over capacity
Express elevators serving only certain floorsAdd a ServableFloors set per Elevator; dispatch strategy filters candidates by whether the requested floor is servable
Multiple elevator banks in a large buildingOne ElevatorController per bank, plus a thin routing layer that picks which bank serves a given floor range
Simulate over real time instead of discrete ticksReplace Tick() with a background timer/task per elevator; same locking discipline applies
Priority requests (fire alarm override)Add a priority flag to InternalRequest/ExternalRequest; queue becomes priority-aware rather than pure SortedSet ordering

Gap to Acknowledge if Asked

The Step implementation shown doesn't opportunistically pick up same-direction requests it passes along the way, it only responds to stops already queued in its current sweep direction. If asked to make it a true LOOK algorithm, say you'd check for compatible pending requests at each intermediate floor, not just the queued stop set.

30-Second Verbal Summary (for opening the answer)

"I'd separate the controller, which only decides which elevator gets a request, from each elevator, which owns its own state machine and stop queue. Dispatch logic sits behind a Strategy interface so nearest-car can be swapped for zone-based later. State is an explicit enum with guarded transitions so moving-with-doors-open is structurally impossible. Concurrency is handled per-elevator with a lock around the stop queue and state, since button presses can arrive at any time from any floor."
